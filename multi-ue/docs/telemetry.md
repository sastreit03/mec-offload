# Source semantics, estimators and remaining measurements

The supplied repaired OAI source is the reference. No OAI files are included as replacements or edited. P01–P11 preservation is by keeping the original sources/image, not by reproducing an upstream scheduler. Basic handset integration is user-reported working; this environment did not repeat it.

Verified by source inspection:

- Existing metrics `rx_bytes` comes from `ul_thr_ue`, a smoothed scheduling-throughput quantity. It is not a cumulative successful unique application-byte counter. `ul_buffer` maps to `sched_ul_bytes`; it is not a UE BSR/application backlog.
- Metrics use ZMQ conflation, so missed samples cannot be reconstructed as a full delivery history. The sparse combined weights wire contains DL `weights`, UL `ul_weights`, and an echoed `ran_index`.
- Missing UE entries use the existing unweighted getter behavior. Existing receive/clear behavior is retained, including no-message/empty-direction handling. There is no new hold timer or minimum grant floor in this bundle.
- Scheduler trace v2 is already compiled/instrumented in the supplied source. `OAI_SCHED_TRACE_FILE` enables it. The main supplied SRK compose entrypoint sets the variable automatically. It records monotonic/realtime mapping, consumption and grant-stage fields, target frame/slot, MCS, symbols, caps, TBS, retries, undersized skips and loss counters.
- That trace has a bounded nonblocking writer and approximately one-second flush interval. Source inspection does not establish acceptable live overhead or fresh100-ms measurement delivery. It lacks complete R53 modulation/coding/layer/DMRS context and is not confirmed unique application delivery.

Implementation consequences:

1. `ran_telemetry` is configured explicitly at100-ms aggregation/report intervals. Reports identify actual measurement windows and validity; a fresh report transport timestamp never makes late trace data fresh. The optional trace reader follows file generations automatically, retains old measurement timestamps and exposes late events.
2. Empty/partial trace windows are not valid throughput evidence. Total UL opportunity is explicitly unavailable; observed residual grant references are logged separately. Per-UE scheduled new-data and retransmission TBS/PRBs remain distinct.
3. `payload_fraction` defaults to null. Scheduled service cannot reduce estimated application demand unless an explicit calibrated conversion is supplied. Confirmed MEC reception always reconciles by max(received,estimated), never addition. Conversion cannot confirm completion, remove a frame on expiry, or credit the same TBS across multiple frames/sessions.
4. `allow_capacity_proxy` defaults false. A realized TBS/PRB ratio is an optional diagnostic proxy, explicitly labeled; it does not satisfy R53. `capacity_table` supports an externally verified reference table keyed by MCS/symbols only for a separately established fixed layer/overhead/configuration context. Current source does not verify that context or adaptation, so a CSV alone cannot establish HC09/R53 acceptance. Do not enable experimental weighted scheduling on this basis.
5. Association uses `rx_bytes` only as a time-varying signature signal. MEC probe-receipt evidence, full interval coverage, correlation and a competing-score margin are required. This is probabilistic lab association. Live four-UE/non-MEC interference tests must measure false matches, ambiguity, probe overhead and recovery tails. No permanent RNTI file is provisioned manually.
6. The network filter uses seconds normalized to1Mbps, q in seconds²/second and P/R/V in seconds². It observes at most once per fully received frame only when the configured throughput-estimate path is explicitly enabled and fresh/valid. No synthetic zero-throughput observation is inserted. Compatible prior calibration is mandatory. Complete-AU admission caches N and L before decode waiting.
7. Live timestamp mapping and gRPC/control round trips require profiling. UE end-to-end compliance needs only its own monotonic clock. Cross-host radio deadlines additionally need the four-timestamp mapping and configured uncertainty threshold. Startup host clock mapping is evidence, not proof of sustained synchronization.

Remaining telemetry gate: establish a source of timely, correctly attributed100-ms grants/capacity context while honoring the user's no-OAI-edit constraint. The included trace can be used for offline comparison/diagnostics, but its current flushing and missing fields do not pass this gate. This is a verified source limitation rather than a chosen bitrate/noise default. Timing, accuracy, bitrate-frontier, residence, conversion and full-core-stack budget values are separate profiling inputs after the system is built.

Strict slot-k→k+1 targeting, late-target rejection and numerology-aligned deadline acceptance (R47–R50 and timing portions of HC06/R57) are deferred explicitly by the user's instruction. The Python muApp retains the current metric-driven `ran_index` path. Scheduler consumption is distinct from the future OTA UL opportunity. No slot timing guarantee is claimed.

Availability (D61): fresh usable reports populate a connection-scoped cached resource estimate. During a brief telemetry interruption, the five-second admission/resumption grace uses that explicitly cached estimate; existing bitrate/DNN choices remain fixed, and changes in radio identity block immediately. After five seconds measured from the last usable window, admissions/resumptions block. Master GoP updates freeze while required inputs are stale. Reconnection clears the old connection cache. Offline initialization and cached estimates are not presented as fresh counters.

Current utility evaluation uses the local decision timestamp for D; mapping to the precise future OTA service opportunity remains unverified with the existing ran_index path. This falls under the documented timing deferral and must not be interpreted as completed R48/R52 target-context validation.
